## What to look for

Findings the same-family reviewers would be least likely to catch. Do not
re-litigate style and do not re-run the gate - both already passed. Prefer:

1. **The install step's failure modes on a real runner.** `curl -sSfL --retry 3
   --retry-delay 2 --retry-all-errors -o "$RUNNER_TEMP/gitleaks.tar.gz" <url>`,
   then `sha256sum -c -`, then `tar -xzf ... -C "$RUNNER_TEMP" gitleaks`. Is
   there a path where the step succeeds without a verified binary, or where the
   scan runs against something other than what was verified? Both Claude
   reviewers concluded there is not; that agreement is exactly the kind this
   request exists to test.
2. **`gitleaks git --redact --verbose .` semantics.** Does it truly scan full
   history in 8.30.1 under GitHub Actions' checkout layout (detached HEAD, single
   fetched ref even with `fetch-depth: 0`)? The full-history claim is verified
   locally on a normal clone, NOT on a runner. If a detached-HEAD checkout narrows
   what `gitleaks git` walks, the second acceptance criterion is weaker than claimed.
3. **Whether dropping the SARIF artifact loses anything** outside this repo's
   `.github/` tree, which is the only place that was grepped.
4. **The new tests' blind spots.** `tests/test_ci_secret_scan.py` asserts on
   workflow structure via `yaml.safe_load`. Which realistic regressions of this
   job would still pass all 5 tests?
