## What the maker was asked to do

`axon seed-lessons` printed its 22 correct status lines, held idempotency, and
then wrote to stderr: `libc++abi: terminating due to uncaught exception of type
std::__1::system_error: recursive_mutex lock failed: Invalid argument`.

Done when: `axon seed-lessons` exits silently on a second (fully idempotent)
run, with a regression test that would catch the message coming back.

The issue suspected an unclosed asyncpg pool. That was falsified during the pass
(LessonStore has no pool; one connection per call, closed in a `finally`;
`close()` is a no-op). The cause identified instead: `axon/embedder/engine.py`
imported onnxruntime and fastembed at module scope, loading the only libc++
consumer in the process on every CLI invocation, for a default model (bge-m3)
that routes through an HTTP chain and never creates an ONNX session. The fix
defers both imports and `preload_dlls()` into `_ensure_model()`.

## What to look for

Findings the same-family reviewers would be least likely to catch. Do not
re-litigate style or re-run the gate - both already passed. Prefer:

- The module-level sentinel pattern (`_ort = None` / `TextEmbedding = None` in
  the `else:` branch of `if TYPE_CHECKING:`, rebound via `global` inside
  `_ensure_model()` / `_detect_providers()`). Is it thread-safe? Two threads
  calling `_ensure_model()` concurrently both run the import and both may call
  `preload_dlls()`. Does that matter for onnxruntime, and does anything in axon
  reach `_ensure_model()` from more than one thread (the MCP server, a
  ThreadPoolExecutor, an anyio worker)?
- Whether deferring `preload_dlls()` out of import time breaks the CUDA case it
  exists for. On the desktop with `onnxruntime-gpu` plus pip-installed
  `nvidia-cudnn-cu12` / `nvidia-cublas-cu12`, is calling it immediately before
  the first `TextEmbedding(...)` still early enough, or did import-time
  execution matter because something else could load the CUDA libs first?
- Whether any OTHER code path in axon depended on `axon.embedder.engine` having
  onnxruntime loaded as a side effect of import - e.g. a module that does
  `engine._ort.something` without going through `_ensure_model()`, or a test
  helper, or the reranker path (`_get_reranker`, fastembed `TextCrossEncoder`).
- The attribution itself. The crash reproduced once in about sixty runs on
  master (exit 134, not the exit 0 the issue claimed), and the fix is argued
  causally (onnxruntime is the only libc++ consumer in the process, measured via
  `DYLD_PRINT_LIBRARIES=1`) rather than by an A/B on the symptom. Is there a
  libc++ consumer in that dylib list I could have missed, or a system framework
  path (getaddrinfo / Network.framework) that could produce the same message
  with onnxruntime absent?
- `tests/embedder/test_engine_providers.py` had one existing test replaced by
  three (the old one pinned "preload_dlls at module import", the contract this
  issue removes). Are the three replacements actually stronger, and do they leave
  a hole the old one covered?
