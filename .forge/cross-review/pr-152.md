## What changed, in one line

`check_capture_gap` stopped passing `repo=` to `find_decision_by_git_hash`, and
`commits_by_repo` was re-keyed from `repo.name` to the repo `Path`.

## What to look for

Findings the same-family reviewers would be least likely to catch. Do not re-litigate style
or re-run the gate - both already passed. Specifically:

1. **The false-negative direction.** Hash identity cannot distinguish two onboarded repos
   that share recent commit history (fork, or a clone with no new commits). If one captured
   and the other's hook is dead, the dead one now reads healthy - a direction the check did
   not have before. Measured 0/45 pairs affected on this machine today, and #151 closes it
   properly. Is there a cheaper guard that does not reintroduce name-keying? Is there another
   way for two DIFFERENT repos to legitimately carry the same commit hash that I have not
   considered (submodules, subtree merges, `git replace`, grafted/shallow clones)?

2. **Environment assumptions in the new code.** `str(repo.relative_to(resolved_dev_root))` is
   OUTSIDE the try/except that degrades store failure to WARN. Both reviewers argued it
   cannot raise because `_onboarded_repos` globs from that same `dev_root` instance. Attack
   that: symlinked repo directories, `AXON_DEV_ROOT` set to a path with a trailing slash or
   a `..` segment, a case-insensitive filesystem, a bind mount.

3. **The `except Exception` blast radius.** It now wraps a loop of N x M store calls instead
   of one call per repo. Can a partial failure mid-loop produce a CONFIDENT wrong verdict
   rather than the intended WARN?

4. **Async correctness.** The lookups are sequential `await`s inside one `asyncio.wait_for`
   with a 5s budget, on a single `SessionStore`. Worst case is ~50 point queries, and there
   is no expression index on `frontmatter->>'git_hash'` (the GIN index on the whole jsonb
   does not serve that predicate). Is the timeout-to-WARN path actually reachable cleanly,
   or can it leave the asyncpg pool half-closed?

5. **The two authorized edits to an existing test file** (`tests/doctor/test_checks_capture_path.py`).
   Adding `find_decision_by_git_hash` to the fake, and seeding `_make_capture_repo` content
   with the repo path so two repos stop getting identical commit hashes. Both were
   pre-authorized and both reviewers adjudicated them as strictly stricter. Verify that
   independently: does ANY test in that file now pass that should fail?
