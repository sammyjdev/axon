## What the maker was asked to do

Owner decision (2026-08-26), option (b), mitigate:

1. Structural delimiters around the untrusted spans (`commit_msg`, `diff_summary`) in the
   classifier prompt, plus explicit framing that instructions inside them are data, not directives.
2. A provenance flag on LLM-inferred ADRs, so a consumer (`get_adrs`, `ask`, the vault export)
   can tell an inferred ADR from one a human wrote.

Owner, verbatim: "The flag is the part that has to hold. Prompt framing is mitigation by
convention - no delimiter reliably stops injection, and treating it as a fix is how this gets
closed while still being exploitable. Provenance degrades gracefully: if the framing fails and a
poisoned ADR lands, it is still labelled as machine-inferred rather than passing as authored."

Explicitly out of scope: blocking inference on suspicious input; any human approval gate.

## What to look for

Findings the same-family reviewers would be least likely to catch. Do not re-litigate style or
re-run the gate. Specifically worth a hostile read:

- **The escape is one-directional by design.** `_fence()` neutralises only the CLOSING tag,
  case-insensitively, on the argument that a forged opening tag cannot terminate a span. Is there
  a construction that escapes the fence anyway - nesting, a partial/split tag across the 3000-char
  `diff_summary` truncation boundary, unicode lookalikes, or the truncation itself severing an
  escape mid-sequence? Note `diff_summary` is truncated BEFORE fencing.
- **Fail-closed default.** `ADR.provenance` defaults to `"llm-inferred"`. Is there any path that
  constructs an ADR with `provenance="human"` from data that did not come from a human? The two
  explicit human call sites are the MCP `save_adr` tool and `pb adr add`.
- **The backfill is a deliberate lie in the safe direction.** All 72 pre-existing production rows
  were labelled `llm-inferred`, including any a human wrote. Is the rendered notice wording
  ("não confirmado como autoria humana") actually true on every row it can appear on?
- **Migration placement.** The `ALTER TABLE` lives in `PostgresDecisionRepository.ensure_schema()`
  rather than a versioned file under `store/migrations/pg/`, because `apply_pg_migrations` is only
  ever called from `PostgresSessionRepository.ensure_schema` and would not run for an ADR-only
  process. Is there a deployment or ordering path where the ALTER does not run before the first
  INSERT that names the column?
- **Consumer coverage.** `ask` was deliberately left untouched on the finding that it never calls
  `get_adrs` and sees ADRs only via the vault markdown that `pb adr sync` writes. Verify that -
  if any other retrieval path reads the `adr` table directly, the label is missing there.
