## What to look for

Findings the same-family reviewers would be least likely to catch. Do not re-litigate style and do not re-run the gate - both already passed. Specific places where a second vendor's lens would help most:

1. **`repo_identity()`'s path arithmetic.** It relies on `Path("/a/b") / "/c/d" == Path("/c/d")` to collapse the relative form (`.git`, `../../../.git`) and the absolute form (a linked worktree) with no branch. Is there a git layout on any platform where `--git-common-dir` returns something this mishandles? Windows drive-relative paths, symlinked repo roots, `GIT_DIR`/`GIT_COMMON_DIR` set in the environment, submodules (`.git` is a FILE there, and the common dir points into `.git/modules/<name>`), `core.worktree`, or `safe.directory` refusal.

2. **Submodules specifically.** The chosen rule takes `git_dir.parent.name` when `git_dir.name == ".git"`, else strips a `.git` suffix. For a submodule the common dir is `<super>/.git/modules/<name>`, so the identity becomes `<name>`. Is that right, wrong, or merely arbitrary? No test covers it.

3. **The migration's safety argument.** `rekey-repo` moves a row when `git cat-file -e <hash>^{commit}` succeeds AND the operator passed `--only-key`/`--all`. Object presence is not reachability and not ownership. Is the `--only-key`/`--all` gate genuinely sufficient, or does it just move the footgun one flag away? Consider alternate object stores, `--reference` clones, forks with shared history, and the fact that the last checkout the operator points at wins.

4. **Concurrency / idempotency of the backfill.** It iterates `all_decisions()` and upserts one row at a time with no transaction. What happens if a git hook captures a decision, or a second `rekey-repo` runs, mid-iteration?

5. **Environment assumptions in the new tests.** They shell out to real `git` and create real worktrees under `tmp_path`. `git worktree add` records an un-canonicalised path on macOS (`/var` vs `/private/var`). The claim is that this is harmless because `repo_identity` only ever returns a `.name` and never compares paths - is that actually true everywhere it is now called?

6. **`_detect_repo()` in `mcp/server.py`** now calls `repo_identity()` with no argument, i.e. from the process CWD, at 10 call sites. Previously it was `_detect_repo_root()` with a `Path.cwd().name` fallback. Any case where the long-lived MCP server's CWD makes this worse rather than better?
