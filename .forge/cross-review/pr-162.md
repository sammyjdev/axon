## What to look for

Findings the same-family reviewers would be least likely to catch. Do not re-litigate
style or re-run the gate - both already passed. Prefer: correctness under inputs the
tests do not generate, security consequences of the chosen approach, and assumptions the
diff makes about the environment.

Three specific things worth an independent eye:

1. **Is the DOM shim in `tests/http/test_dashboard_xss.py` a faithful enough model?**
   The whole test rests on one asymmetry (`textContent` escapes on serialization,
   `innerHTML` splices raw). If the shim is wrong in some third respect - attribute
   serialization, `style` handling, child ordering, the `firstChild`/`removeChild`
   loop the implementation now depends on - the test could pass for a reason unrelated
   to escaping. It was verified RED against the unmodified file, which rules out the
   most common version of this, but not all of it.
2. **Did the rewrite change rendered output in a way no test covers?** The old code
   emitted a single space as literal text between spans inside an innerHTML string;
   the new code appends `document.createTextNode(" ")`. Same for the empty states and
   the sparkline's `style="height:Npx"` becoming `bar.style.height`. Nothing asserts
   the visual result, only that no markup was injected.
3. **Attribute-context escaping.** The sparkline now passes hostile values through
   `setAttribute("title", ...)`, which is safe in a real browser, but the test observes
   it through the shim's own escaper. Worth confirming there is no remaining path where
   response data reaches an attribute or a style value without going through the DOM API.
