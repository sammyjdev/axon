## What the maker was asked to do

From issue #141, verbatim:

> `axon health` reports sqlite / pgvector / vault / git and cannot see the capture path at all. That blind spot cost twelve days.
>
> ## What happened
>
> `pipx uninstall axon-mcp` removed `~/.local/pipx/venvs/axon-mcp/` on 2026-08-10 at 11:21:08. All 13 repos' hooks kept naming that interpreter. Every AXON hook ends in `2>/dev/null || true`, so each commit ran a `bad interpreter` and said nothing.
>
> Measured after the fact:
>
> - 2026-08-07: 23 commits, 22 decisions carrying a `git_hash`.
> - 2026-08-10 onwards: 28 commits, 0 decisions. Every commit that day is timestamped 14:54 or later - after the uninstall - so there is no counterexample in the window.
> - The same root cause had also killed `~/.local/bin/axon-compact-save` (PostCompact hook, exit 127).
>
> Throughout, `axon health` answered `ok` on all four lines.
>
> ## What the command must answer
>
> Three questions, none of which any current command asks:
>
> 1. **Does each hook's interpreter exist, and can it import what the hook needs?** Not `os.path.exists` - actually run `<interpreter> -c "import axon.adr.lesson_pool"` for the interpreter named in each `.git/hooks/post-commit` across known repos. The 2026-08-22 audit found `lesson-retraction.py` working only by accident, through a `.pth` in the pyenv global; a path check would have called that healthy.
> 2. **Does the installed version match `HEAD` of master?** The install is deliberately a snapshot (an editable install would let a feature branch become what every repo executes), so it defaults to drifting. On 08-11 the MCP served code that lacked three modules merged the day before.
> 3. **Is the newest decision consistent with the newest commit?** A repo with commits from today and no decision since last week is the signature of a dead hook.
>
> ## Done when
>
> `axon doctor` fails loudly on a repo whose hook interpreter is missing, on an installed version behind master, and on a capture gap - each verified by a test that breaks the corresponding condition on purpose.

## What to look for

Findings the same-family reviewers would be least likely to catch. Do not re-litigate style or re-run the gate - both already passed. Prefer: correctness under inputs the tests do not generate, security consequences of the chosen approach, and assumptions the diff makes about the environment.

Specific areas where a second-vendor lens would be most useful here:

1. **`check_hook_interpreters` executes a path read out of a file on disk.** It parses `.git/hooks/post-commit` with `shlex.split` and runs token 0 as a subprocess with `-c "import axon.hooks.git_event"`. The hook file is repo-local and thus attacker-influenced by anyone who can write into a repo under the dev root (a cloned repo, a malicious `.git/hooks` shipped in an archive). Judge whether a diagnostic command executing that path is acceptable, and whether the 15s timeout plus `capture_output` is a sufficient bound. The pre-existing installer bakes `sys.executable` in, so the value is normally trusted - the question is what happens when it is not.

2. **`_onboarded_repos` walks two fixed depths of the developer's home tree by default** (`AXON_DEV_ROOT`, else `load_runtime_config().engine_root.parent`, in practice `~/dev`). Consider what this does on a machine where that parent is large, is a network mount, or contains symlinked directories. Note the two globs cannot follow a symlinked `.git` because a worktree's `.git` is a file, but a symlinked repo DIRECTORY is a different case.

3. **`check_install_freshness` recomputes git blob shas from installed bytes** (`sha1(b"blob <len>\0" + data)`) and compares against `git ls-tree -r HEAD`. This assumes no clean/smudge filter and no `.gitattributes` (true today). Judge whether the assumption is stated loudly enough, and whether a false FAIL here - which tells the user to reinstall - has a worse consequence than we think.

4. **`check_capture_gap` decides "gapped" from a set intersection over the last 5 commit hashes.** Consider inputs the tests do not generate: a repo whose last 5 commits are all merge commits, a shallow clone, a repo in a detached-HEAD or mid-rebase state, and a repo whose `git log` succeeds but returns commits from a different branch than the one the hook fired on.

5. **Exit-code blast radius.** These are the first checks in `run_all_checks()` that can return FAIL from MACHINE state rather than from data-root state. `axon doctor` exits 2 on FAIL, so anything scripting `axon doctor` now hard-fails on a dev box with a stale install. Judge whether that is the right default or whether the machine-probing checks should be opt-in.

Known and already tracked, so do not spend the review on them: the renamed-repo false positive in `capture.gap` (#146), `index-vault` missing from the entry-point app (#147), and the two-level scan ceiling (named in a `ponytail:` comment).
